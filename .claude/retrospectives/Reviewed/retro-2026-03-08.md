## Findings

### Finding 1: STALL — Pipeline stopped after Dev+stop-hook verification
- **Type:** STALL / PATTERN
- **Severity:** P0
- **What happened:** After `/dev` completed and the stop hook fired ("Code was edited but no dev server is running"), the orchestrator correctly ran preview verification. However, after verification was complete, it ended its assistant turn and waited for user input. The user had to say "continue" to trigger `/qa`.
- **Expected behavior:** Per CLAUDE.md Dev Pipeline: "Fully autonomous. No approval gate." After Dev completes (including any inline verification), the orchestrator should immediately invoke `/qa` without user input.
- **Root cause:** The stop hook injected a new user-turn message into the conversation (`[Preview Required] Code was edited...`). The orchestrator handled it but treated the verification completion as a natural end-of-turn rather than resuming the pipeline.
- **Suggested fix:** Add a note to the CLAUDE.md Dev Pipeline section:
  ```
  **Stop hook handling:** If a stop hook fires between pipeline stages (e.g. preview verification),
  handle the hook inline and immediately continue to the next stage without waiting for user input.
  Completing hook verification is not a pause point.
  ```

### Finding 2: STALL — Pipeline stopped after QA PASS
- **Type:** STALL / PATTERN
- **Severity:** P0
- **What happened:** `/qa` returned "QA complete — Issue #96: PASS. 5/5 ACs verified, moved to In Review." The orchestrator stopped and waited for user input. User said "continue" to trigger `/review`.
- **Expected behavior:** After QA PASS, the orchestrator should immediately move the issue to Code Review and invoke `/review`.
- **Note:** The QA skill handoff text is correctly neutral ("Do NOT suggest next steps or address the user"). The stall is purely orchestrator behavior — it treated the skill's return as a natural conversation endpoint.
- **Suggested fix:** This recurs despite the retro-2026-03-07-2.md showing it was fixed for issue #55. The difference appears to be the **watcher context** — the pipeline was triggered by a scheduled task rather than a direct user instruction. The scheduled task SKILL.md already says "Execute the steps below now — do not greet the user or wait for input" and "Dev Pipeline (fully autonomous, no pauses, no user confirmation needed)". But the main orchestrator (responding to the watcher task) is still stopping. Consider adding explicit "do not stop between stages" to the orchestrator-level watcher context:
  ```
  # In watcher SKILL.md, add after each pipeline stage description:
  After each skill returns, immediately continue to the next stage without outputting to the user.
  ```

### Finding 3: STALL — Pipeline stopped after Review APPROVED
- **Type:** STALL / PATTERN
- **Severity:** P0
- **What happened:** `/review` returned "Review complete — PR #107 (issue #96): APPROVED. All checks pass." The orchestrator stopped again. User asked "are you still working automatically?" before saying "continue".
- **Expected behavior:** After Review APPROVED, the orchestrator should immediately run the auto-merge steps (post approval comment, merge, move to Done, post final report).
- **Note:** Same root cause as Finding 2 — each skill return is treated as a conversation endpoint in the watcher context.

### Finding 4: REGRESSION — Stalls return in watcher context despite retro-2026-03-07 fixes
- **Type:** PATTERN
- **Severity:** P1
- **What happened:** retro-2026-03-07-2.md (issue #55) verified that Finding 1 from the optimization audit was "FIXED, EFFECTIVE — Zero unintended stalls." This run shows 3 stalls.
- **Root cause hypothesis:** Issue #55 was triggered by a direct user message ("implement #55"). The orchestrator was in a continuous agentic session responding to the user. This session was triggered by a **scheduled task watcher**, which creates a different conversational context. The orchestrator may behave differently when the "user" is the task scheduler rather than a human typing in chat.
- **Key distinction:** In a regular session, the orchestrator keeps invoking skill tool calls in sequence within the same turn. In the watcher context, each skill invocation may be completing a response turn, causing the orchestrator to end the turn and wait for input.
- **Suggested fix:** In the watcher SKILL.md, be more explicit that the orchestrator must chain all pipeline stages in a single agentic session with no outputs to the user between stages:
  ```
  **IMPORTANT:** Do not output any text to the user between pipeline stages.
  Invoke each stage's skill immediately after the previous one returns.
  The only output should be after the entire pipeline is complete.
  ```
